# Engine reasoning

Every logic choice and every number in the engine, with the evidence behind it. Generated by `python -m engine.reasoning` from `selection_log.json`, `config.yaml`, `sensitivity.json` and `disputes.py`; the hand-written explanations live in `engine/reasoning.py`.

## 1. How a logic was chosen

Each engine component (12 checkpoints, in dependency order) has 2-4 candidate logics. At checkpoint *k* every candidate of component *k* is scored with all other components fixed, the best is kept, and then every earlier component *j* is re-checked: if switching *k* to its runner-up changes any verdict *j* decides, *j*'s candidates are re-scored and *j* switches if another candidate now wins by at least `score.switch_margin` = 0.5 (coordinate ascent, at most `score.max_passes` = 3 passes).

**Confidence score (0-10) = correctness + safety + explainability + robustness**

| part | weight | measured as | why this weight |
|---|---|---|---|
| correctness | `score.w_correct` = 4 | share of the rows this component decides that match truth.csv (verdict + reason). Rows = the codes it owns **plus every row on which its candidates disagree** (contested rows), so false positives and side effects count. Risk: out-of-sample AUC, (AUC - `score.auc_chance`) / (1 - `score.auc_chance`). Cost: accounting invariants. | correctness carries the brief's 25% safety criterion plus the edge-case contract: the largest single weight |
| safety | `score.w_safety` = 3 | backtest: decide on days 0-22, replay the recommendations on the held-out week; 0 unsafe = full, 1 unsafe = `score.safety_one_unsafe` = 1, more = 0 | an unsafe downsize is the worst possible outcome; weighted just below correctness only because it is binary and already near-guaranteed by replay |
| explainability | `score.w_explain` = 2 | share of this component's fired findings visible in the output with value, threshold and result: >= `score.explain_full` -> full, >= `score.explain_half` -> x `score.partial` | the brief's 20% transparency criterion; half of correctness because a clear wrong answer is still wrong |
| robustness | `score.w_robust` = 1 | verdict flip rate when every threshold of the component moves +/- `score.perturb`: < `score.flip_good` -> full, < `score.flip_ok` -> x `score.partial` | tie-breaker: a logic that flips when thresholds move 10% is fragile, but fragility alone should not beat correctness |

- **Acceptance bar** `score.accept_min` = 7: 7/10 = full safety + explainability (5) plus at least half correctness (2): a component must be right more often than not
- **Switching margin** `score.switch_margin` = 0.5: re-loops only switch an earlier choice for a real improvement (half a point), not for noise
- **Tie-break:** fewer parameters wins (a simpler logic that is equally right is easier to explain and to trust).
- **Bias guard:** truth.csv was written alongside the original plan, so correctness is also logged on bulk (real-trace-resampled) rows only, and safety and robustness do not use truth.csv at all. Where the data contradicts a label, the label is listed as a dispute (section 5) instead of bending the logic to it.

### Engine-wide design decisions (apply to every candidate)

- **Shrink-considered.** Capacity vetoes and the recurring-peak check run only for VMs an average-based tool would cut (mean < `peaks.looks_wasteful_mean` or CPU P < `candidates.underused_cpu`). A busy VM cannot be 'rejected' for a shrink nobody proposed.
- **Leak on every VM.** A leaking VM's memory percentiles are an artefact of its restart cycle, so neither a downsize nor an upsize is trustworthy until it is fixed.
- **Recurring peak blocks resize only.** A scheduled peak forbids shrinking, not scheduling around it; the off-hours map keeps the peak window on by construction (dev-etl-04's nightly job).
- **Went quiet outranks upsize.** Recent behaviour invalidates older evidence, so it sits in the data-flag class.
- **NO_CHEAPER_PLAN vs PEAK_REPLAY_FAILED.** NO_CHEAPER_PLAN only when memory rules out every cheaper plan; when CPU is the limit the honest explanation is the replay of what an average-based tool would do.
- **Upsize only when busy on average.** A VM averaging under 20 % that touches 90 % is batchy, not starved.
- **Floor applies to compute changes.** Deleting or releasing a resource with no running workload has no blast radius, so the Rs 500 attention floor does not apply to it.
- **Service groups.** Members get the same target, sized on the busiest member; if any member cannot shrink, none do.
- **Linear CPU scaling.** Peak Replay assumes CPU % scales with vCPU count (stated assumption; headroom and the one-step prod rule absorb the error).

## 6. Alerts, presets, scorecard, benchmark

**Alerts** (`engine/alerts.py`, `data/alerts.json`). Every alert states the number, the threshold and why.
- *Usage spike*: robust z of the 30-min rolling **log-ratio** to the same hour-of-week median, sigma = `alerts.mad_to_sigma` x MAD. Three decisions, each fixing a measured false-alarm source: (1) rolling the *deviation* instead of the raw value stopped windows straddling an hour boundary from comparing a peak hour with a quiet one (prod-billing-01 at 12:00 was '77% vs 3%'); (2) scaling MAD to sigma makes 4 a real 4-sigma threshold (plain 4 x MAD is ~2.7 sigma); (3) the log scale treats the fitted multiplicative day-to-day drift (Bitbrains sd 0.59) as normal spread. Spike alerts fell 56 -> 36 -> 11, the strongest being the planted one-off (prod-reports-02, z 15) and the random bursts (prod-queue-02).
- *Cost increase*: alerts on the provisioning **step** only (the day cost changes), not on the following days while the 7-day average catches up. Threshold x1.1 is measured: billing is flat on 87% of team-days and the steps in the window are +12.9% / +12.7% (new VMs) vs +2.4% / -1.7% / -3.4%; the plan's x1.2 missed both new-VM events.
- *Capacity trend* (CPU p95, memory p95, disk, volumes): significant least-squares slope over the last 14 days reaching 90% within 30 days (critical within 7). *Level shift* / *possible compromise* (CPU and egress both > 3x). *Memory leak*, *under-provisioned*, *monitoring missing*, *budget overrun* (forecast = spent + 7-day run-rate x days left vs 1.25 x first-quarter spend).

**Presets** (`engine/presets_report.json`): savings move only 18.6% -> 19.5% from max-performance to max-savings because Peak Replay, the memory caps, the recurring-peak veto and the one-step prod rule are preset-independent; none of the presets produces an unsafe change in the held-out week.

**Scorecard** (`data/scorecard.json`) and **benchmark** (`engine/benchmark.json`): summarised in ASSUMPTIONS.md.
