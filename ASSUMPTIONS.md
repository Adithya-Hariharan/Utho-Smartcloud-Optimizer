# Assumptions

Two halves, as planned: the **data half** (prices, simulated fleet, fitted traces, data-quality faults) is `data/DATASET.md`; the **engine half** (every threshold, preset and rule the decisions use) is below. Generated by `python -m engine.assumptions` from `engine/config.yaml` and the measured outputs; full reasoning for each logic choice and each number is in `engine/REASONING.md`.

## Pricing and billing (summary of the data half)

- Prices are **illustrative**, modelled on Utho's public Basic tiers, INR, excluding GST; 730 h per month; all regions priced the same; no reserved-instance discounts or egress charges.
- Block storage Rs 8/GB-month, snapshots Rs 4/GB-month, public IP Rs 200/month.
- A stopped VM pays for its disk only (`stopped_vm_billed = false`): scheduling saves compute, never storage.
- Savings are **sequential**, never additive: each action is priced on what the previous one left.

## Presets

Presets change only the sizing percentile, the CPU target and the replay overload budget. Measured on this fleet (same selected logic):

| preset | percentile prod/non-prod | CPU target prod/non-prod | replay budget min/month | saving | unsafe in held-out week | risk levels |
|---|---|---|---|---|---|---|
| max_performance | 99.5 / 99.5 | 60 / 60 | 0 / 0 | Rs 118,052 (19.2%) | 0/46 | {'Medium': 23, 'Low': 29, 'High': 1} |
| default | 99 / 95 | 70 / 80 | 0 / 30 | Rs 123,452 (20.0%) | 0/47 | {'Medium': 23, 'Low': 30, 'High': 1} |
| balanced | 95 / 95 | 80 / 80 | 30 / 30 | Rs 123,452 (20.0%) | 0/47 | {'Medium': 23, 'Low': 30, 'High': 1} |
| max_savings | 90 / 90 | 90 / 90 | 60 / 60 | Rs 123,452 (20.0%) | 0/47 | {'Medium': 23, 'Low': 30, 'High': 1} |

**Reading.** Savings move only from 19.2% to 20.0% across presets. A lower percentile does make more VMs *look* underused, but Peak Replay's overload line, the memory caps, the recurring-peak veto and the one-step prod rule are preset-independent and refuse the extra cuts. The binding constraint is replayed overload, not the sizing percentile: the safety gates are doing real work, and no preset buys savings with unsafe changes on this fleet.

## Scale benchmark

1,062 VMs (9x the demo fleet, 8,647,371 metric rows) processed in **61.22 s** on one process (57.6 ms per VM; clean 5.94 s, evidence + decisions 41.39 s, alerts 13.89 s; peak memory ~763 MB) on Windows / Python 3.11.7. single process, no parallelism; per-VM work is independent, so it parallelises across processes. Beyond ~10k VMs: pre-aggregate hourly percentiles in a columnar store (DuckDB / ClickHouse) and run the engine per region in parallel.

## Engine simplifications (stated, not hidden)

- CPU % is assumed to scale linearly with vCPU count in Peak Replay; headroom and the one-step prod rule absorb the error.
- Memory used (GB) is assumed unchanged by a resize; only the percentage changes.
- 30-day window: yearly seasonality is invisible, which is why the `seasonal_peak` tag exists.
- Aggregate CPU hides a single saturated thread.
- No reserved instances, savings plans or egress charges; prices are illustrative.
- Recommendations are never auto-applied: every one carries before/after evidence and a rollback.
